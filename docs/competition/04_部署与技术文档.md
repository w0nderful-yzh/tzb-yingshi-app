# 04 部署与运行说明 + 系统设计与技术开发文档

## 1. 文档说明

本文面向比赛评委和技术复现人员，描述当前最终代码实际能够运行的系统。所有结论以代码、配置、依赖文件、数据库模型、Android 调用和运行产物为依据。历史 README、研究目录和计划功能不构成部署事实。

本文使用四种运行状态：

- **默认自动启动**：根目录 Compose 直接启动的 PostgreSQL 与主 FastAPI；
- **手动启用**：已有可执行实现，但须安装外部模型/SDK、连接硬件并单独启动；
- **Shadow / 实验**：只用于观测、对比或辅助证据，不创建正式告警；
- **当前未接入**：代码存在，但不在 Android 当前调用链或没有数据桥接。

当前一键部署边界必须先明确：`docker compose up` 只启动 PostgreSQL 和主 FastAPI。Camera–Radar 引擎、雷达 HTTP 服务、IWR6843ISK UART bridge、心理工作器均需在 Windows 主机单独启动。诈骗 ASR 运行在主 FastAPI 进程内，不是独立微服务。

## 2. 系统总体架构

### 2.1 可直接绘图的分层结构

```text
感知设备层
├─ 萤石摄像机（视频、SDK解码PCM）
└─ TI IWR6843ISK（CLI串口 + Data串口，3D People Tracking）
          │
          ▼
AI分析层
├─ Camera：OpenSDK → RTMDet → RTMPose3D → 45帧/15Hz Pose → 6折BioSTGCN
├─ Radar：UARTParser → 点云/trackData → 特征窗 → calibrated causal TCN
├─ Fraud：PCM → 20ms帧 → WebRTC VAD → Paraformer partial/SenseVoice final
└─ Psychology：OpenSDK视频 → OpenFace → 目标轨迹启发式 → MCCL×2 → XGBoost
          │
          ▼
风险状态 / 事件层
├─ CameraEvidence + RadarEvidence
│  → 时空关联 → Radar Eligibility Gate → Camera-led Evidence Fusion v2
├─ Fraud Evidence → 分类器/规则 → S0-S5状态机 → 可选LLM复核 → RiskEvent
└─ PHQ-8辅助分数 → no_risk/mild/moderate/severe snapshot
          │
          ▼
后端服务层
├─ 主FastAPI :8000
│  ├─ PostgreSQL 16（正式用户、设备、RiskEvent、处置记录）
│  ├─ REST / WebSocket
│  └─ 本地读取 psychology snapshot 或HTTP读取外部风险源
├─ Camera–Radar引擎 :8001（手动）
├─ Radar FastAPI :8010（手动）
└─ Psychology worker（手动，无端口；可选只读API端口未固定）
          │
          ▼
Android应用层
├─ 登录并选择已绑定老人
├─ EZOpenSDK实时视频 + PCM上传
├─ 跌倒概览（1秒轮询）
├─ 诈骗事件（REST初始化 + WebSocket增量）
└─ Care心理状态（进入/重试时读取）
```

### 2.2 跌倒真实数据流

```text
萤石设备
→ Windows EZOpenSDK 解码帧
→ RTMDet 人体检测
→ RTMPose3D 生成3D WholeBody Pose
→ 15 Hz时基、45个有效Pose帧、步长8
→ 六折BioSTGCN
→ CameraEvidence
                     ┌→ IWR6843ISK CLI/Data UART
                     │  → TI UARTParser/3D People Tracking
                     │  → calibrated causal TCN
                     └→ RadarEvidence
→ 相机人框/雷达轨迹时间空间关联
→ Radar Eligibility Gate
→ Camera-led Evidence Fusion v2
→ 多模态引擎 `/api/multimodal/camera-led-associated/latest`
→ 主后端 `/api/v1/fall-risk/overview`
→ Android 跌倒页面
```

与题设链路相比，真实实现有三点需要修正：

1. CameraEvidence 和 RadarEvidence 是并行产生后在引擎内关联，不是 CameraEvidence 串行“流入”RadarEvidence；
2. Camera-led Evidence Fusion v2 的风险概率保持摄像头分数，雷达改变的是证据模式、支持/冲突状态和说明，不做新的加权概率，也不能否决摄像头高风险；
3. v2 当前 `affects_app_result=true`、`shadow_only=false`、`affects_alerts=false`，会更新 App 状态；正式告警由主后端在 `/api/v1/fall-risk/overview` 轮询该结果时边沿触发写入 `FALL_SUSPECTED` RiskEvent（一次幕次一条，60 秒冷却，状态回落自动重新武装）。

### 2.3 诈骗真实数据流

```text
Android EZOpenSDK原生音频回调
→ 16kHz / mono / signed 16-bit PCM
→ 每1秒、32000字节 POST `/api/v1/devices/{id}/audio-pcm`
→ 后端 AppPcmRelaySource
→ 20ms帧 + WebRTC VAD
→ Paraformer Streaming（每600ms产生partial，可选）
→ SenseVoiceSmall（语句结束后的final，可选但比赛链路开启）
→ 文本/情绪/声学风险Evidence
→ 字符TF-IDF + 校准LogisticRegression分类器
→ deterministic rules + S0-S5状态机
→ OpenAI-compatible LLM复核（默认关闭）
→ S2+ Fraud RiskEvent
→ PostgreSQL
→ REST事件列表 + WebSocket `risk_event.upserted`
→ Android诈骗事件页
```

当前演示采用 `app_relay`，并非后端从 HLS/RTMP/FLV 拉音频。服务端云媒体拉流代码已实现，但属于手动切换能力。LLM、语义检索、近期上下文和 preliminary 事件默认关闭，不是默认判定前提。

### 2.4 心理真实数据流

```text
萤石视频
→ Windows EZOpenSDK HEVC解码
→ 临时H.264 MP4
→ OpenFace FeatureExtraction CSV
→ 多人轨迹启发式：最长出现 + 较低运动轨迹
→ kps / gaze / pose / AU视觉特征
→ 每clip 1800帧，7个clip
→ MCCL模型1 + MCCL模型2
→ XGBoost回归
→ PHQ-8辅助估计与risk_level
→ 原子写入 `home_out/latest/<subject_sha256>.json`
→ 主后端 `/api/v1/psychology/overview`
→ Android Care页面
```

当前部署推理没有音频融合，也没有注册身份的人脸识别。“目标老人”由视频轨迹启发式选择。心理结果为辅助评估，不作为医疗诊断。

Psychology API 的 `operating_mode` 在当前响应模型中固定为 `shadow`：它可以显示在 Care 页面，但不创建正式 RiskEvent，也不应描述为临床诊断结果。

## 5. 配置说明

### 5.1 配置文件边界

- 根目录 `.env`：由 Compose 与主后端读取；不得提交真实值。
- `backend/app/modules/fall/multimodal_engine/.env`：只由多模态引擎读取，避免与主后端数据库配置混用。
- Radar 服务直接读取启动进程环境变量，不会自动读取根 `.env`。
- 心理工作器读取命令行参数和进程环境变量，不会自动读取根 `.env`。
- Android Base URL 是构建期 Gradle 属性，不从后端 `.env` 读取。

## 8. 萤石平台与设备接入

### 8.1 平台在当前系统中的作用

1. **Open Platform API**：主后端和多模态/心理进程用 AppKey/AppSecret 换取 AccessToken，并可请求直播地址和平台报警记录。
2. **EZOpenSDK Android**：App 使用 5.30.2 SDK，以后端下发的 AppKey、AccessToken、deviceSerial、channel 创建原生播放器；视频不经过主后端转发。
3. **EZOpenSDK Windows**：摄像头跌倒和心理工作器使用 PC OpenSDK 解码真实设备码流。
4. **PCM 回调**：Android 播放器原生回调输出 PCM，App 归一为 16 kHz/单声道/16-bit 并上传主后端。
5. **直播协议**：开放平台代码支持 HLS、RTMP、FLV；当前 Android 原生 SDK 播放只使用 deviceSerial/channel，当前诈骗链路使用 App PCM relay。
6. **平台报警**：Webhook 和 alarm polling 已实现但默认关闭。开启后会写 `ys7_signal_inbox`、`visual_events` 及可选 raw JSON；它不是本项目诈骗/跌倒 AI 的替代物。

项目算法边界：萤石提供设备、鉴权、码流/SDK播放和可选平台事件；RTMDet、RTMPose3D、BioSTGCN、Radar TCN、融合、VAD/ASR/诈骗规则、MCCL/XGBoost 和 RiskEvent 由本项目完成。

### 8.2 token 与设备绑定

主后端若配置 `APP_YS7_ACCESS_TOKEN` 会使用静态 token；否则通过 AppKey/AppSecret 获取并缓存，在接近过期或平台返回 token 失效码时刷新重试。AppSecret不进入 Android。

Android `live-sdk-session` 的真实响应只有 AppKey、AccessToken、deviceSerial、channel 和 expires_in；当前播放器代码没有接收验证码字段，也没有调用客户端 `setPlayVerifyCode`。因此当前 Android 主播放链路要求设备在该账号/token下可直接播放。`APP_YS7_DEVICE_VERIFY_CODE` 和多模态引擎的 `EZVIZ_DEVICE_VERIFY_CODE` 只供 Windows心理/摄像头工作器使用，不能写成Android已注入验证码。

当前 App 没有新增萤石设备的完整 UI。比赛设备通过演示数据初始化或数据库管理流程绑定：根 `.env` 的 deviceSerial/channel 在 seed 时写入 `devices`，家庭关系由 `family_bindings` 建立。修改设备后，若已有持久化 volume，单纯重启不会覆盖现有行，应更新数据库或清理专用演示 volume 后重新 seed；不要在有正式数据的环境删除 volume。

验证绑定：登录后调用 `GET /api/v1/devices`，确认返回设备在线状态；再调用 `GET /api/v1/devices/{device_id}/live-sdk-session`，只检查字段存在和过期时间，不打印 token。

### 8.3 “08_平台调用证据”建议截图

应单独截取并脱敏以下证据：

1. 萤石开放平台应用概览：应用名称、归属主体、AppKey 仅保留首尾少量字符，AppSecret完全遮挡；
2. 设备列表/详情：设备在线、通道号、设备归属，序列号和验证码遮挡；

5. Android日志：SDK初始化成功、播放器开始播放、PCM callback有数据，不截 access token；
6. 后端 `/integrations/ys7/media/status`：媒体源为 app_relay、worker状态和最近音频时间；

1. 先启动主后端、Radar API和多模态引擎；

## 10. 毫米波雷达模块部署

### 10.1 硬件与数据解析

当前实现针对 TI IWR6843ISK。板卡连接后 Windows 会出现 CLI 与 Data 两个串口。`ti_official_bridge.py` 使用官方 `UARTParser` DoubleCOMPort 模式：先通过 CLI 发送 `ISK_6m_default.cfg` 并核验 `Done`，再从 Data 口解析 pointCloud、trackIndexes、trackData，包括位置、速度、加速度和置信度。

COM口、官方 parser、cfg 路径全部来自 `TI_OFFICIAL_OUTPUT_COMMAND_JSON`，不是从 Android或数据库读取。示例 COM5/COM6 仅为代码默认，部署必须以设备管理器实际端口为准。

### 10.2 最终部署模型

当前使用 `tcn_0p5_1p0_specificity_operating_point_v1.pt` 和 `calibrated_normalization_real_gaussian.json`。服务默认测试 checkpoint 只用于证明 API 能启动；比赛真机应显式设置 calibrated TCN 配置。calibrated TCN 输出仍标记 shadow/suppressed/formal=false，作为融合辅助证据，不单独创建正式事件。

### 10.3 正常、数据不足与融合接收判定

- **服务正常**：`GET :8010/health` 返回200、`model_loaded=true`；
- **硬件正常**：`radar_connected=true`、`source_mode=REAL`、最近帧时间更新、point count/frame rate有观测值；
- **推理正常**：`GET /api/radar/latest` 返回200；当前calibrated路径在 `calibrated_tcn_prediction` 内提供 `pre_fall_score`、`data_quality`、`score_valid`、`tcn_risk_state`；
- **数据不足**：返回 `INSUFFICIENT_DATA`、`WARMUP`、`score_valid=false`，原因可能是窗口未满、帧间隔、点数、轨迹稳定性或传感器断流；
- **融合已收到雷达**：`:8001/api/multimodal/camera-led-associated/latest` 的 `radar.available=true` 且时间更新；只有 `alignment.association_state=MATCHED` 且 v2 eligibility 为可用时，雷达才真正进入v2证据模式。

雷达服务与引擎之间为 HTTP 轮询，默认轮询间隔 0.05 s。该数值是 API poll interval，不是 IWR6843ISK 的传感器帧率；实际帧率只能从实时帧时间统计。

## 11. Camera–Radar 融合模块部署

### 11.1 当前并行链路

引擎在启动时开启 Radar poller 和 shadow sampler，但摄像头必须由 guard-session启动。相机与雷达 evidence 按时间和空间标定关联；默认同步容差2.0 s。Radar Eligibility Gate使用1.2 s历史窗，至少2个轨迹样本、3个点、轨迹稳定度0.60、质量0.25，并检查速度突变和高度容差。

`FUSION_ALIGNMENT_CALIBRATION_PATH` 必须对应当前房间、相机视角和雷达安装位置。移动任一设备后继续沿用旧标定会导致 `UNMATCHED` 或错误关联。

### 11.2 正式 App 结果与 Shadow 分离

| 输出 | 用途 | 是否影响App | 是否创建正式告警 |
|---|---|---:|---:|
| `/api/multimodal/camera-led-associated/latest` 中 v2 | 当前客厅风险状态 | 是 | 是（主后端轮询时边沿触发写 `FALL_SUSPECTED`，非引擎直接写） |
| `/api/multimodal/latest` fixed/quality weighted | 基线观测 | 否 | 否 |
| temporal associated | 实验时序关联 | 否 | 否 |
| associated risk augmentation | shadow增强解释 | 否 | 否 |
| calibrated Radar TCN | v2辅助RadarEvidence | 间接 | 否 |

### 11.3 MATCHED 和降级验证

```powershell
curl.exe http://127.0.0.1:8001/api/multimodal/camera-led-associated/latest
```

检查：

1. `camera.available=true`，有 `camera_score` 和 `camera_risk_state`；
2. `radar.available=true`，房间和时间戳与当前雷达一致；
3. `alignment.association_state=MATCHED`；
4. `camera_led_evidence_fusion_v2.radar_eligible=true`，并结合 `reason_codes` 判断是否通过门控；

7. `fall_event` 是展示状态，不应据此声称 PostgreSQL已有跌倒事件。

## 12. 诈骗识别模块部署

### 12.1 当前默认判定组件

诈骗分类器在进程内从 `backend/app/modules/fraud/data/train.jsonl` 构建，不需要外部分类器 checkpoint；规则来自 `rules.json`。VAD使用 WebRTC VAD，ASR模型来自 FunASR/ModelScope。规则、分类器和状态机为正式判定主干，LLM仅为可选复核层。

音频参数和节奏：客户端每1秒上传32000字节；服务端拆为20 ms帧；VAD启动200 ms、静音结束700 ms、前后各300 ms缓冲、最长10 s；Paraformer partial间隔600 ms。以上是配置门限，不是端到端告警延迟。

### 12.2 逐级验证

1. **EZOpenSDK音频回调**：Android logcat出现播放器音频帧/relay计数，且不是持续0字节；
2. **PCM上传**：后端访问日志出现 `POST /api/v1/devices/{id}/audio-pcm` 2xx；接口头 `X-Audio-Sample-Rate=16000`；
3. **VAD**：后端日志/状态出现 speech start/end、utterance长度，不应把环境静音当语音；
4. **ASR**：streaming revision出现 partial文本，语句结束出现 final transcript；若final为空，检查SenseVoice ready状态；
5. **Evidence**：日志/内部响应出现命中规则、classifier probability、emotion/audio evidence；
6. **Fraud状态**：session状态从S0向S1-S5演进，`GET /api/v1/fraud/sessions/{session_id}` 可读取；
7. **PostgreSQL事件**：FINAL 判定达到 S2 及以上（S1 待观察仅会话内观察，不产生消息）后 `risk_events.type=FRAUD_SUSPECTED`，包含 `fraud_state`、`fraud_score`、`fraud_evidence`；
8. **App显示**：WebSocket收到 `risk_event.upserted`，诈骗事件页出现新卡片；断开WS后重新进入页面仍能通过REST加载数据库事件。

直接调试文本链路可使用 `POST /api/v1/fraud/analyze`，但 Android 当前不调用它；比赛端到端验证仍应使用真实 PCM 上传。

## 13. 心理状态模块部署

### 13.1 资源与工作周期

工作器需要萤石PC OpenSDK、FFmpeg/ffprobe、OpenFace、两个MCCL checkpoint和XGBoost文件。每个clip按15 Hz恒定时基使用1800帧，至少1500有效帧；一轮固定7个clip。源设备实际帧率可能偏离15 Hz，工作器会按配置抓取和转码，不能把15 Hz写成所有摄像机的实测帧率。

### 13.2 snapshot 与 Care 映射

工作器用原子替换写 `home_out/latest/<sha256(subject_key)>.json`。主后端使用老人 `external_subject`计算相同哈希并读取；若两个subject不一致，Care会显示没有最新 assessment。

主后端返回字段 `operating_mode="shadow"`。这表示该结果是面向日常关怀的辅助观察；页面展示与正式事件告警是两条独立链路。

风险映射：

| estimated PHQ-8 | risk_level |
|---:|---|
| `<10` | `no_risk` |
| `10–14` | `mild` |
| `15–19` | `moderate` |
| `>=20` | `severe` |

验证顺序：

1. worker日志出现OpenSDK抓流、OpenFace CSV、clip计数和assessment完成；
2. latest JSON的 `assessment_id`、`assessment_state`、`estimated_phq8_score`、`risk_level`、`data_quality` 更新时间正确；
3. 主后端 psychology overview返回相同 assessment；
4. Care 页面显示本轮；若本轮 processing，则显示状态和 `latest_completed` 上一轮；
5. 结果只作为关怀辅助信息，不触发诊断结论。

### 15.2 事件处置接口边界

- Android实际使用 `PATCH /events/{id}/status`，状态为 `acknowledged`、`false_alarm` 或 `resolved`，并携带当前 `version` 做并发控制；
- `POST /events/{id}/confirm` 已实现，但当前 Android 主要走 status patch；
- `POST /events/{id}/intervention-reminder` 和历史回放接口当前返回501，不列入比赛功能；
- WebSocket只推送当前主后端进程产生的实时事件；断线后以 `GET /events` 的PostgreSQL数据恢复。

### 16.3 两套 RiskEvent

系统仍存在两套独立 RiskEvent：

1. 主后端 PostgreSQL：UUID、JSONB、正式 App 事件和处置；
2. 多模态引擎 MySQL：BIGINT、`evidence_json`、原型monitoring/dashboard事件。

当前没有同步或统一层，多模态相机/雷达/融合事件开关均应保持关闭，避免把原型库写入误认为App事件。正式诈骗 RiskEvent 只写PostgreSQL（S2+ 才写，S1 待观察仅会话内观察）；跌倒正式事件由主后端在 overview 轮询中边沿触发写 `FALL_SUSPECTED`；家属删除消息为软删除（`RESOLVED + RETRACTED`），保留审计记录。

## 19. 安全与隐私说明

1. AppKey、AppSecret、AccessToken、设备验证码、数据库密码和LLM Key不得硬编码到文档、截图、APK源码或日志。Android只接收短期AccessToken和AppKey，AppSecret保留服务端。
2. 比赛测试账号、测试设备与正式账号/设备应隔离；演示口令必须替换Compose占位值。
3. PostgreSQL保存账户、绑定、设备元数据、诈骗session、RiskEvent及处置；音频原始PCM当前在内存中处理，不作为正式文件归档，但转写、证据摘要可能进入事件JSON。
4. 心理模块会产生临时视频/OpenFace特征和latest assessment；Radar产生点云/轨迹JSONL；Fusion产生shadow JSONL；启用萤石signal时可能归档raw事件。
5. 日志可能包含姓名、subject key、设备序列号、房间、视频时间窗、转写文本、风险分数和错误上下文。比赛前应清理或脱敏日志。
6. 必须脱敏：姓名、手机号、用户ID、deviceSerial、验证码、画面URL、token、语音文本、心理评分明细、定位/房间细节和截图中的人物面部。
7. 老人视频、音频和心理数据属于高敏感数据。采集、展示、保存和用于模型验证前应取得明确授权，限定用途与保留时间，并提供删除机制。未经许可不得把原始视频或语音样本放入公开提交包。
8. Android bearer token存于App私有SharedPreferences，但没有额外加密；比赛机应使用测试token，演示后退出登录并清理应用数据。

## 21. 评委从源码到看到 App 结果的最短部署路径

以下路径控制在12步，前提是比赛包已按许可准备外部视觉模型、萤石PC SDK、OpenFace、TI Toolbox和三个可用Python环境。

1. **解压并进入仓库**：打开含 `compose.yaml` 的根目录；预期可见 `android/` 和 `backend/`。
2. **填写两份本机配置**：由模板创建根 `.env` 和多模态 `.env`，填数据库、演示账号、萤石设备、fall/psych/app_relay/ASR开关及外部模型路径；预期无未替换的必填占位符。
3. **启动基础服务**：执行 `docker compose up -d --build postgres backend`；预期 `docker compose ps` 中postgres/backend均healthy，`:8000/api/v1/health`返回成功。
4. **启动雷达服务**：设置最终TCN、normalization、room和TI bridge命令，从 `backend/app/modules/fall` 启动Uvicorn 8010；预期 `/health` 为 `model_loaded=true`。
5. **连接雷达真机**：接好IWR6843ISK的CLI/Data端口，POST `:8010/api/radar/real`；预期CLI配置成功，`radar_connected=true`、latest不再503。
6. **启动多模态引擎**：执行 `scripts/start-multimodal-engine.ps1 -PythonPath <MULTIMODAL_PYTHON> -HostAddress 0.0.0.0 -Port 8001`；预期宿主机和Docker主后端均可访问fall-live、radar status、camera-led端点。
7. **启动心理工作器**：以与数据库老人一致的subject-key运行 `psychology_worker_main.py --capture-mode opensdk --loop`；预期latest JSON产生，主后端psychology overview可读。
8. **确认诈骗模型就绪**：查看 `:8000/api/v1/integrations/ys7/media/status`；预期source为app_relay、`models_ready=READY`、classifier ready。
